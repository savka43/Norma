# Архитектура системы — проектное решение

Основание предметной области: две предоставленные ЛР, требования из которых
зафиксированы в `docs/requirements/` и `docs/architecture/domain-model.md`.
Исходные DOCX не включены в репозиторий. Раздел описывает **согласованный
технический подход** и предложения, а не подменяет UML ЛР №2.

## 1. Стиль

**Модульный монолит + feature-based структура.** Один backend-приложение FastAPI,
один основной PostgreSQL, отдельный рабочий процесс для длительных внешних проверок.
Физически микросервисы не требуются; модульность обеспечивается контрактами и ответственностью.

### Backend

```text
backend/
  app/
    main.py
    core/
      config.py
      database.py
      security.py
      models/
    api_v1/
      auth/
      users/
      supervisor_groups/
      theses/
      stages/
      documents/
        export/
      comments/
      plagiarism/
      notifications/      # проектное расширение, не UC из ЛР
    common/
  alembic/
  tests/
  pyproject.toml
```

Типовая директория: `views.py` (тонкий HTTP), `schemas.py` (Pydantic),
`crud.py` (SQLAlchemy), `dependencies.py` (Depends), `service.py` **только**
при наличии переходов состояний, транзакционной оркестрации или правил.
`plagiarism/client.py` — SOAP-адаптер; `documents/export/` — формирование файлов.
**Не** добавлять общий Repository layer.

### Frontend

```text
frontend/src/
  app/                   # router, providers
    styles/
      globals.css        # reset, общие токены и базовая типографика
  pages/                 # страницы + Page.module.css рядом
  features/
    auth/
    supervisor-groups/
    theses/
    stages/
    document-editor/     # Lexical, A4 pagination, toolbar, outline, autosave
      components/
        EditorToolbar.tsx
        EditorToolbar.module.css
    comments/
    plagiarism/
    formatting/
  shared/
    api/                 # HTTP client
    ui/                  # свои компоненты с *.module.css
    lib/
    types/
```

React + TypeScript + Vite + React Router + TanStack Query + TanStack Form;
Lexical для документа; **CSS Modules (`*.module.css`)** и собственные UI-компоненты.
**Без Tailwind CSS, shadcn/ui, React Hook Form, Zod.**
TanStack Query — серверное состояние, TanStack Form — формы; не вводить глобальный
state manager, пока не возникнет необходимость.

Правила CSS: компонент и его `Component.module.css` лежат рядом; импортировать
классы как `styles`; глобальный `globals.css` использовать только для reset,
типографики и CSS-переменных (цвета, отступы, радиусы, шрифты). Общие UI-элементы
с их модулями — в `shared/ui/`. Селекторы компонентов не должны протекать глобально.
Пример: `import styles from './EditorToolbar.module.css'` и
`<div className={styles.toolbar}>...</div>`.
Подробнее: `docs/decisions/ADR-003-css-modules.md`.

## 2. Модульные границы

| Модуль | Владеет | Не должен владеть |
|---|---|---|
| auth/users | идентичность, роль, вход, учётные записи | правила подтверждения этапов |
| supervisor_groups | группы руководителя, участники | содержимое текста |
| theses | работа, студент, руководитель, тема | внешний SOAP клиент |
| stages | этапы, сроки, отправка/подтверждение, прогресс | форматирование DOCX |
| documents | рабочий JSON, сохранение, контрольные версии, импорт/экспорт | баллы антиплагиата |
| comments | замечания и их статус/привязки | полномочия назначения группы |
| plagiarism | задания проверки, интеграция API, сохранённые результаты | изменение текста версии |
| notifications | события и доставка уведомлений (расширение) | основной source of truth статусов |

Переходы между модулями через понятные функции/сервисы; недопустимо обновлять
в обход `stages` поля его статуса из случайного HTTP обработчика.

## 3. Работа с документом и версиями

- **Рабочий документ:** `documents.content JSONB` в формате сериализованного Lexical EditorState,
  `revision` — номер сохранения, `schema_version` — версия формата.
- **Автосохранение:** клиент посылает `content` + `expected_revision`;
  сервер проверяет владельца/lease и ревизию, атомарно записывает новую.
  Устаревшая ревизия → `409 Conflict`, не молчаливое затирание.
- **Edit lease:** ограниченная серверная аренда редактирования одним пользователем;
  продление, истечение и восстановление при потере связи. Чтение параллельно разрешено.
- **Контрольная версия:** неизменяемый снимок для отправки этапа, замечаний,
  проверки заимствований и экспорта.
- **Комментарии:** ссылка на `DocumentVersion`, автор, текст, статус,
  anchor на путь блока исходной версии + диапазон UTF-16; при утрате текущей
  привязки замечание не удаляется. Backend реализован в ADR-013, UI отсутствует.
- **Импорт DOCX:** в ЛР1 предусмотрена загрузка версий; реализовать
  преобразование поддержанных элементов DOCX в структуру редактора,
  с явным сообщением об элементах, которые невозможно корректно импортировать;
  оригинальный файл хранится независимо от нормализованного документа.
- **Экспорт:** из контрольной версии + шаблона формировать DOCX; PDF получать
  из валидного документа с проверкой вёрстки. Настройки оформления — отдельный версионируемый шаблон,
  а не набор случайных inline-стилей в редакторе.
- **Одновременное редактирование:** не поддерживается, WebSocket/Yjs/CRDT не нужны.

## 4. Workflow этапа — центральный процесс ЛР

```text
Руководитель создаёт группу и задаёт этапы/сроки
           ↓
Студент редактирует текст / импортирует DOCX
           ↓
Сохраняется контрольная версия
           ↓
Студент отправляет конкретный этап на проверку
           ↓
Руководитель просматривает версию
           ↓
[замечания и доработка] ИЛИ [явное подтверждение этапа]
           ↓
Система обновляет ход выполнения и просрочки
```

Пользователь согласовал enum: `in_progress → in_review → changes_requested/completed`;
после правок `changes_requested → in_review`, подтверждение всегда явное.
Все этапы обязательны, прогресс — доля подтверждённых (без весов).
См. `product.md`, раздел 9 и ADR-004.

Backend этого workflow реализован (ADR-013): каждая отправка создаёт снимок,
решение обязательно называет проверенную версию, история отправок/решений
неизменяема. Замечания и вычисляемый diff доступны через защищённый API.
Пока нет областей этапов, отправляется весь документ: любые правки рабочего
текста/шаблона блокируются при наличии `in_review`. Редактирование других глав
и frontend полного цикла ещё не реализованы.

## 5. Внешняя проверка «Антиплагиат»

```text
UI → POST check → DB job/status → worker (SOAP/WSDL)
                                ↓
                      polling API + report
                                ↓
                      DB result/history → UI polling
```

Задания должны быть **долговечными**, то есть обрабатываться после закрытия браузера
и переживать перезапуск HTTP процесса. FastAPI BackgroundTasks сами по себе
недостаточны как гарантия долговечности; использовать отдельный worker и
персистентное состояние задания (проектный выбор подлежит реализации).
Не делать автоматический повтор после ошибки без отдельного действия пользователя
— это требование API «Антиплагиат».

Подключение настраиваемое: WSDL / URL компании / технический пользователь,
хранимые вне Git. Отчёты и метрики сохранять по фактическим возможностям API.
Документация: https://docs.antiplagiat.ru/ru/api/.

## 6. Безопасность и эксплуатация

- Все данные конкретной ВКР и её группы доступны только связанным актёрам;
  проверки на backend обязательны.
- Серверные операции редактирования и решения по этапам транзакционны.
- Публичный тестовый API не получает реальные ВКР и персональные данные.
- PostgreSQL хранит метаданные/JSONB и, в первом инкременте импорта,
  отдельные BYTEA оригиналов/изображений (ADR-011). Экспорты вычисляются из
  неизменяемой версии/шаблона в ограниченном запросе, файлы не сохраняются
  в БД (ADR-012); перенос крупных blobs при необходимости уточняется отдельно.
- Docker Compose: backend, frontend, postgres, worker, file storage при необходимости.
- Студент регистрируется самостоятельно, руководитель добавляет его в свою группу.
  Технический bootstrap руководителя не создаёт третью бизнес-роль.
  Реализованы Argon2id, отзываемые серверные cookie-сессии и CLI bootstrap;
  решение и ограничения — [ADR-007](../decisions/ADR-007-auth-sessions-bootstrap.md).

## 7. Тестирование

- Backend: pytest для правил этапов, прав доступа, ревизий, истории, проверок;
  интеграционные тесты PostgreSQL, миграций и мок SOAP.
- Frontend: Vitest/Testing Library для форм и редактора; Playwright — основные UC.
- Integration API test с публичным аккаунтом — только на несекретных текстах,
  не в каждом обычном CI запуске.

## 8. Редактор и оформление

Lexical — ядро редактирования, **не движок полной постраничной вёрстки**.
Один Lexical JSON, независимый слой компоновки страниц A4, шаблоны оформления
(базовый ГОСТ 7.32-2017, параметры изменяемы), импорт DOCX в семантическое
содержимое, экспорт DOCX/PDF. Визуальный diff и история замечаний сохраняются.
Не внедрять ML-корректор переносов. Подробно: `docs/requirements/editor.md`,
`docs/architecture/editor-design.md`, ADR-001 и ADR-004.

## 9. Что не включать без нового согласования

Третьи роли кафедры, нормоконтроль как отдельный процесс, новые этапы
сверх согласованного сценария, микросервисы, Repository-layer ради паттерна,
Realtime collaboration, неизвестную «универсальную» систему ГОСТ без конкретных требований.
