# Предметная модель: ЛР №2 → реализация

**Источник:** ЛР №2, описание девяти классов на с. 4–7 и десяти отношений на с. 8–10.
Исходная UML-модель — концептуальная, **не** буквальная схема таблиц или Python-классов.

## Десять отношений по ЛР2 (с. 9–10)

1. **НаучныйРуководитель (1) → ГруппаСтудентов (*)**: один руководитель создаёт несколько групп.
2. **ГруппаСтудентов (1) → Студент (1..*)**: группа включает студентов; студент в одной группе руководителя.
3. **Студент (1) ↔ ВКР (1)**: у каждого студента одна ВКР в рассматриваемом контексте.
4. **НаучныйРуководитель (1) → ВКР (*)**: руководитель ведёт много ВКР, у ВКР один руководитель.
5. **ВКР (1) ♦→ ЭтапВКР (1..*)**: композиция, этапы принадлежат ВКР.
6. **ВКР (1) ♦→ ВерсияРаботы (*)**: композиция, у ВКР может быть ноль и более версий.
7. **ВерсияРаботы (1) → ПроверкаАнтиплагиат (*)**: повторяемые проверки; ноль до первой.
8. **ВерсияРаботы (1) → Замечание (*)**: замечания привязаны к версии.
9. **ШаблонОформления (1) → ВерсияРаботы (*)**: один шаблон применяется к многим версиям.
10. **НаучныйРуководитель (1) → Замечание (*)**: руководитель — автор замечания.

`♦` — обозначение композиции здесь; в БД жизненный цикл будет контролироваться
FK, сервисными правилами и политикой удаления (не автоматическим каскадным
уничтожением истории).

## Предлагаемое отображение на SQLAlchemy / PostgreSQL

| Доменный класс | Предлагаемые модели/таблицы | Примечание |
|---|---|---|
| НаучныйРуководитель + Студент | `User` / `users` с ролью и профилями | Один общий auth-механизм; не теряем понятие двух актёров |
| ГруппаСтудентов | `SupervisorGroup` / `supervisor_groups`, `group_memberships` | Группа НЕ академическая учебная группа |
| ВКР | `Thesis` / `theses` | Фиксация связи student_id/supervisor_id |
| ЭтапВКР | `ThesisStage` / `thesis_stages` | Порядок, срок, состояние; история решений отдельно |
| ВерсияРаботы | `Document`, `DocumentVersion` | `Document` — рабочий Lexical JSONB; `DocumentVersion` — неизменяемый снимок |
| ШаблонОформления | `FormattingTemplate`, `FormattingTemplateVersion` | Настраиваемая версия шаблона, связь с экспортом/версией |
| ПроверкаАнтиплагиат | `PlagiarismCheck` / `plagiarism_checks` | Внешние ID, состояния, метрики, ссылки/отчёты |
| Замечание | `Comment` / `comments`, при необходимости `CommentAnchor` | Автор, версия, цитата, текст, статус, устойчивый anchor |

Дополнительные технические сущности, **не являющиеся новыми классами ЛР2**:
`DocumentAsset` (изображения/вложения), `DocumentEditLease` (блокировка редактора),
`StageSubmission`, `StageStatusEvent` (история отправок, переходов и решения), `AuditEvent`
(история значимых действий), `BackgroundJob` (надёжный workflow внешней проверки).
Добавлять их можно по мере подтверждения соответствующих инвариантов.

## Строгие инварианты для проектирования

- У каждой ВКР один студент и один руководитель; повторная привязка ВКР к студенту
  требует согласованной модели учебных лет или явного изменения ЛР.
- У этапов есть упорядоченность и срок; изменения этапов делает руководитель.
- `DocumentVersion` неизменяема после фиксации; комментарии и проверки ссылаются
  на определённую версию, даже если рабочий документ уже поменялся.
- Проверка антиплагиата создаёт собственную запись при повторе; результат предыдущей не затирается.
- Замечание сохраняется даже при перемещении/удалении исходного фрагмента.
- Пароли хранятся только как хэш и не возвращаются в API.

## Несовпадения с ранними идеями — не скрывать

1. **Роли:** ранее обсуждались нормоконтролёр и заведующий кафедрой; ЛР1 их не содержит.
   Базовый продукт следует ЛР1, новые роли — только отдельным изменением требований.
2. **Версии:** ЛР2 описывает файл каждой версии; для встроенного редактора принят JSONB
   и снимки. Нужно сохранить выгрузку файла и импорт, чтобы покрыть старый UC-01.
3. **Контроль:** ЛР делает акцент на проверке *этапов*, а не на общей машине
   состояний «Черновик → Нормоконтроль → Допуск». В центре реализации — `ThesisStage`.
4. **Научный руководитель:** административные возможности ограничены его
   студентами и группами; глобальное управление — отдельный вопрос.

## Принятые уточнения модели (не добавленные классы исходной UML)

- `User(role=student|supervisor)` — общая безопасная учётная запись. Студент регистрируется сам; руководитель набирает свою `SupervisorGroup` из уже зарегистрированных студентов. Первая учётная запись руководителя создаётся технической bootstrap-командой.
- `ThesisStage.status` — enum `in_progress`, `in_review`, `changes_requested`, `completed`. `StageSubmission` связывает **конкретный этап** и **неизменяемую версию всего документа**; в модели при необходимости хранится ссылка на section/block, который соответствует этапу. `StageStatusEvent` сохраняет историю отправок/возвратов/подтверждений.
- Все этапы обязательны; `progress_percent = 100 * count(completed) / count(all_stages)` при наличии хотя бы одного этапа. Удаление подтверждённого этапа с потерей истории запрещено.
- `Document.content` — Lexical JSONB; `Document.schema_version` для миграций формата. Вёрстка на листы A4 — производное представление, а не таблица `document_pages` с отдельным содержимым.
- `DocumentVersion` содержит snapshot Lexical JSON и ссылку на `FormattingTemplateVersion`; `DocumentOriginalFile` или ссылка на исходный импортированный DOCX сохраняется отдельно для отслеживаемости импорта.
- `Comment`: `version_id`, `author_id`, `quote`, `anchor`, `is_detached`, `status`; закрытые скрываются по умолчанию, но остаются в истории и diff.
- Сравнение версий — вычисляемый результат между двумя immutable версиями, отдельная таблица diff не обязательна.
- `FormattingTemplateVersion`: неизменяемый JSON параметров листа, полей, шрифтов, отступов, заголовков, нумерации, таблиц и подписей. Базовая предустановка ориентирована на ГОСТ 7.32-2017, но проверка использует текущие выбранные значения.

Дополнения отражают решения пользователя, **не являются буквальной UML ЛР №2**.

## Реализованная часть схемы (фаза 2)

Модель `User` и миграция `0002_users` реализованы: общая таблица `users`,
UUID, ФИО, уникальный без учёта регистра email, `password_hash`, роль
`student|supervisor`, время создания и поля профиля. Студенту требуется учебная
группа, руководителю — должность и кафедра; поля другой роли должны быть `NULL`.
Это техническое уточнение хранения исходных атрибутов ЛР; обоснование и ограничения —
в [ADR-006](../decisions/ADR-006-user-model.md).

Реализованы регистрация студента, login/logout/me и CLI bootstrap руководителя.
`AuthSession` (`0003_auth_sessions`) хранит SHA-256 случайного токена, FK пользователя,
время создания и истечения; удаление пользователя каскадно отзывает его сессии.
Это техническая сущность аутентификации, не новый класс исходной UML или бизнес-роль.
Подробности — [ADR-007](../decisions/ADR-007-auth-sessions-bootstrap.md).
Проверяются действующая сессия и роль.

`SupervisorGroup` и `GroupMembership` (`0004_supervisor_groups`) реализуют
UC-07/FR-07: руководитель владеет своими группами, зарегистрированный студент
имеет максимум одно назначение во всех группах. Группа хранит название и год
начала учебного года; участие — FK студента как PK, FK группы и время добавления.
Академическая группа в профиле студента не меняется при назначении.
Роль и принадлежность группы проверяет backend; уникальность назначения — БД,
включая конкурентные запросы. Удаление связанных записей ограничено FK RESTRICT,
автоматического переноса и создания ВКР нет.
Детали и границы — [ADR-008](../decisions/ADR-008-supervisor-groups.md).
Связи с ВКР и соответствующие права добавлены первым backend-инкрементом фазы 3 ниже.

## Реализованная часть схемы (первый backend-инкремент фазы 3)

`Thesis`, `ThesisStage` и `StageEvent` (`0005_theses_stages`) реализуют создание
одной ВКР для студента своей группы, настройку обязательных этапов, порядка и сроков,
историю настройки и сводку прогресса. `Thesis` хранит уникального студента
(FK на участие в группе), руководителя, тему, даты, ревизию плана и время создания.
У `ThesisStage` — стабильный UUID, FK ВКР, имя, позиция, срок и enum четырёх
согласованных состояний. Уникальность позиции в ВКР проверяется при commit.
Новые этапы всегда `in_progress`; статус нельзя менять через настройку.

`StageEvent` — дополнительная техническая сущность аудита настройки: актёр,
ревизия ВКР, вид `created|updated`, снимки до/после и время. Сдвиги остальных
этапов также фиксируются. Изменения плана и истории транзакционны; блокировка
ВКР и `expected_revision` защищают конкурентные сохранения (`409`).
FK `RESTRICT` сохраняют связи участия, ВКР, этапов и истории.

Прогресс вычисляется из всех этапов, при пустом плане — `null`.
Общий статус ВКР отдельно пока не хранится. `StageSubmission`, `StageStatusEvent`
и переходы проверки ещё не реализованы: им нужны неизменяемые `DocumentVersion`.
Frontend отсутствует, фаза 3 целиком не завершена.
Правила доступа, сроков, допустимой настройки и ограничения —
[ADR-009](../decisions/ADR-009-thesis-stage-planning.md).

## Реализованная часть схемы (backend-инкремент фазы 4)

Миграция `0006_documents` добавляет `Document`, `DocumentEditLease`, `DocumentVersion`,
`FormattingTemplate` и `FormattingTemplateVersion`. Документ создаётся явно студентом
своей ВКР, уникален по `thesis_id`; содержит единый валидируемый Lexical JSONB,
версию схемы, ревизию, счётчик контрольных версий и выбранный снимок шаблона.
GET не создаёт записей. Шаблон принадлежит руководителю; его версии хранят
неизменяемые параметры оформления и последовательные номера.

Одна аренда на документ содержит владельца, случайный UUID и срок действия.
Мутации блокируют строку документа, проверяют аренду и ожидаемую ревизию.
Сохранение увеличивает ревизию, явный снимок — счётчик контрольных версий.
`DocumentVersion` хранит текст, версию схемы/шаблона, ревизию, номер, автора,
комментарий и необязательную ссылку на исходную версию восстановления.
Restore атомарно заменяет рабочий текст и создаёт новую контрольную версию.
Прежние снимки не переписываются; UPDATE обеих таблиц версий запрещён также
триггером PostgreSQL, FK используют `RESTRICT`.

Чтение — студенту своей ВКР и её руководителю, редактирование — студенту.
Backend-проверки документов/версий и привязки к шаблону реализованы.
Frontend/A4, diff, импорт/экспорт и workflow проверки ещё не реализованы.
Доступное подмножество Lexical и границы —
[ADR-010](../decisions/ADR-010-document-storage-versions-leases.md).
