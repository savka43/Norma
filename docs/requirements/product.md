# Требования к продукту — рабочая спецификация

**Статус:** рабочая редакция 2.0; ключевые решения из раздела 9 приняты пользователем.
**Первичные источники:** ЛР №1 «Построение Business Use Case», с. 3–8;
ЛР №2 «Построение Use Case» (по содержанию — UML-диаграмма классов), с. 3–10.
Исходные DOCX предоставлены пользователем для подготовки требований, но
**не входят в репозиторий**. Настоящая спецификация фиксирует извлечённые сведения.

## 1. Назначение и границы

Система предназначена для автоматизации **подготовки и сопровождения этапов выполнения ВКР**:
студент работает над текстом и отправляет этапы на проверку, научный руководитель
формирует группу, настраивает этапы и сроки, проверяет, оставляет замечания,
подтверждает этапы и контролирует прогресс.

Цель, зафиксированная в ЛР1: объединить разрозненные действия и сведения о ходе работы,
уменьшить ручное оформление, потери версий/замечаний и нарушения сроков (ЛР1, с. 3–5).

## 2. Участники (по ЛР1)

- **Студент:** работает с документом своей ВКР, версиями, оформлением,
  проверкой заимствований и замечаниями; отправляет этапы руководителю.
- **Научный руководитель:** сопровождает студентов, формирует собственную группу,
  устанавливает этапы/сроки, проверяет работу, оставляет замечания, подтверждает этапы,
  видит состояние групп. В исходной предметной модели совмещает роль администратора.

Отдельный актёр-администратор, нормоконтролёр и заведующий кафедрой **не предусмотрены** в ЛР1.
Техническая учётная запись оператора системы/начальная инициализация требуют отдельного решения:
не превращать это автоматически в третью бизнес-роль.

## 4. Данные (по ЛР2)

Исходные девять классов: `НаучныйРуководитель`, `ГруппаСтудентов`, `Студент`,
`ВКР`, `ЭтапВКР`, `ВерсияРаботы`, `ШаблонОформления`, `ПроверкаАнтиплагиат`, `Замечание`.
Их атрибуты, операции и десять отношений — `docs/architecture/domain-model.md`.

ЛР2 фиксирует, в частности: один студент — одна ВКР, один руководитель может
сопровождать много ВКР, в ВКР есть этапы, у версий есть проверки и замечания.

## 6. Бизнес-правила, известные из ЛР

- Студент прикреплён к одной группе научного руководителя в контексте выполнения ВКР (ЛР2, с. 9).
- На одну ВКР приходится один студент и один научный руководитель (ЛР2, с. 9).
- Руководитель задаёт этапы и сроки, подтверждает выполнение этапов (ЛР1, с. 4–5).
- Этап может быть отправлен на проверку и подтверждён руководителем (ЛР2, с. 5).
- Любая загруженная версия сохраняется в истории, предыдущие не теряются (ЛР1, с. 5).
- Замечание связано с версией и автором, имеет признак исправления (ЛР2, с. 6, 10).
- Проверка на заимствования связана с конкретной версией и может выполняться неоднократно (ЛР2, с. 6, 9).

| NFR-05 | Тестируемость | Unit, API/DB integration и E2E для основных UC |
| NFR-06 | Экспорт | DOCX/PDF создаются из зафиксированного содержимого и шаблона |
| NFR-07 | Воспроизводимость | Проект запускается через Docker Compose и миграции из чистого окружения |
| NFR-08 | Безопасность интеграций | Секреты не хранятся в Git; реальная ВКР не отправляется в публичный тестовый аккаунт |

Производительность, лимиты размеров, доступность, сроки хранения, резервное копирование,
регламент удаления данных и юридические аспекты — **не определены источниками**.
Перед production-эксплуатацией их следует определить отдельно.

## 8. Требования к проверке заимствований

- Для учебной интеграции используем тестовый SOAP/WSDL API «Антиплагиат».
- Запуск для конкретной версии, хранение внешнего идентификатора, статуса и
  доступных метрик; повторный запуск — отдельная запись истории.
- Показ фаз и ошибок; асинхронная обработка с восстановлением после закрытия страницы.
- Отчёты по правам и фактическим возможностям тестового аккаунта.
- Учёт ExternalUserId длиной не более 40 символов (по документации API).
- Публичный тестовый аккаунт — только для безопасных демонстрационных документов.

Основание расширения: https://docs.antiplagiat.ru/ru/api/ (дата проверки: 15.11.2026).

## 9. Принятые решения пользователя (2026-11-16)

1. **Состояния этапа:** `in_progress` (в работе), `in_review` (на проверке), `changes_requested` (нужны правки), `completed` (завершён). Разрешены отправка `in_progress/changes_requested → in_review`, решение руководителя `in_review → changes_requested/completed`. Повторное редактирование после возврата возможно. История переходов обязательна.
2. **Завершение:** только явное действие научного руководителя «Подтвердить выполнение этапа», даже если замечаний нет.
3. **Обязательность и прогресс:** все этапы обязательны; `completed_count / total_count × 100%`. Этапы и сроки задаёт руководитель. Количество этапов должно быть больше нуля для отправки на проверку. Веса не используются.
4. **Регистрация:** студент регистрируется самостоятельно, руководитель добавляет уже зарегистрированного студента в свою группу. Академическая группа и группа руководителя — разные сущности. Как создаётся первоначальная учётная запись руководителя — техническая bootstrap-процедура, не новый бизнес-актёр.
5. **Редактор:** Lexical, листы A4, автоперенос текста, минимум кнопок; основная идея — **правильное оформление по выбранному шаблону уже при наборе**. Поддержка импорта DOCX с нормализацией; не гарантировать точную передачу произвольной сложной верстки Word. См. `docs/requirements/editor.md`.
6. **Оформление:** шаблон по умолчанию ориентируется на **ГОСТ 7.32-2017**, но поля, шрифт, интервалы, стили заголовков, списков и подписей — **редактируемые параметры**. Проверка и исправление всегда используют именно активную сохранённую версию шаблона, не константы из кода.
7. **Комментарии:** завершённые/устаревшие замечания скрываются из основного вида по умолчанию, но доступны в истории вместе с исходным текстом версии. Удалённые/перенесённые фрагменты не теряются благодаря снимкам и сравнению версий.
8. **Антиплагиат:** официальный тестовый SOAP API со сокращённой базой, достаточно рабочего workflow. Неизвестные лимиты не придумывать: сделать конфигурируемыми и показывать ответ внешнего сервиса.
9. **Diff:** сравнение любых двух сохранённых версий с подсветкой вставок, удалений и изменений. Определение перемещений best-effort, отсутствие распознавания перемещения не должно искажать историю.
10. **ML-помощник по сложной верстке и переносам:** лишь идея на будущее, **не реализовывать сейчас**. Нужны только базовые детерминированные правила автоматической компоновки.

## 10. Действительно оставшиеся технические вопросы

- Форматы и лимиты импорта конкретных сложных DOCX-элементов (формулы, вложенные таблицы, сноски): оценить при реализации и документировать, не обещать без тестов.
- Техническая реализация pagination для Lexical (он не предоставляет Word-подобную постраничную верстку автоматически).
- Точные лимиты тестового API и виды отчётов зависят от доступного аккаунта: учитывать динамически.

Выбор auth cookies/сессий и bootstrap руководителя выполнен в
[ADR-007](../decisions/ADR-007-auth-sessions-bootstrap.md); бизнес-правила не изменены.

Эти детали **не препятствуют началу кодирования**. Изменение принятых бизнес-правил требует отдельного согласования.
