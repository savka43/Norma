# CLAUDE.md

Этот файл задаёт контекст для Claude Code при работе с репозиторием. Читай его перед любой задачей.

## О проекте

**Информационная система сопровождения выполнения этапов написания ВКР.**

Система ведёт выпускную квалификационную работу студента от выдачи задания до загрузки итогового комплекта в ЭОС. Она решает четыре задачи:

1. **Контроль этапов.** Этапы ВКР со сроками, статусами и отметками руководителя.
2. **Совместная работа.** Студент загружает версии, руководитель оставляет замечания и принимает этапы.
3. **Автоформатирование.** Система сама приводит загруженный .docx к требованиям оформления кафедры и выдаёт исправленный файл и отчёт об изменениях.
4. **Антиплагиат.** Интеграция с открытым API сервиса «Антиплагиат». Функционал API ограничен, клиент пишется под реально доступные методы.

Итоговый комплект выгружается в личный кабинет студента в **ЭОС** (электронная образовательная среда вуза). Доступов к ЭОС пока нет, поэтому интеграция делается через адаптер с заглушкой (см. «Внешние интеграции»).

Система проектируется **мультикафедральной**, но сначала внедряется для одной кафедры (ИС). Всё, что зависит от кафедры, хранится в БД как настройки, а не зашивается в код: шаблон этапов, шаблон оформления, порог оригинальности.

## Роли

| Роль | Что может |
|---|---|
| `student` | Видит свою ВКР и этапы, загружает версии, запускает форматирование и проверку на антиплагиат, отвечает на замечания |
| `supervisor` | Видит своих студентов, просматривает и сравнивает версии, оставляет замечания, принимает или возвращает этапы |
| `dept_admin` | Настраивает кафедру: шаблон этапов, шаблон оформления, порог антиплагиата, назначение руководителей; видит сводку по кафедре |
| `admin` | Управляет кафедрами и пользователями всей системы |

Доступ к данным ограничивается кафедрой и привязкой «студент ↔ руководитель». Проверка прав выполняется на бэкенде в каждом эндпоинте, а не только на фронте.

## Доменная модель (основные сущности)

- `Department` — кафедра; хранит настройки.
- `User` — пользователь с ролью и привязкой к кафедре.
- `Thesis` — ВКР: тема, студент, руководитель, учебный год, текущий статус.
- `StageTemplate` — шаблон этапа кафедры: название, порядок, смещение или дата срока, обязательные документы.
- `Stage` — этап конкретной ВКР: срок, статус, отметка руководителя.
  Статусы: `not_started → in_progress → submitted → (revision ↔ submitted) → accepted`.
- `DocumentVersion` — версия файла: исходник, отформатированный файл, номер, автор, хэш, время загрузки.
- `FormattingProfile` — шаблон оформления кафедры (JSON с правилами, версионируется).
- `FormattingRun` — запуск форматирования: входная и выходная версии, отчёт об изменениях, статус.
- `PlagiarismCheck` — проверка на антиплагиат: версия, внешний id, статус, процент оригинальности, ссылка на отчёт.
- `Comment` — замечание к версии или этапу, с привязкой к разделу или фрагменту и статусом `open` или `resolved`.
- `FinalPackage` — итоговый комплект: ПЗ, презентация, аннотация, отзыв, справка о заимствованиях. Хранит статус выгрузки в ЭОС.
- `Notification` — уведомление пользователю.

Стандартный шаблон этапов кафедры ИС (seed-данные):
1. Задание на ВКР
2. Глава 1 — анализ предметной области
3. Глава 2 — обоснование технических решений и проектирование
4. Глава 3 — реализация и предзащита
5. Введение, заключение, список литературы, приложения и окончательное оформление
6. Проверка на антиплагиат
7. Итоговый комплект (выгрузка в ЭОС)

## Стек

**Backend**
- Python 3.12, **FastAPI**, Pydantic v2
- **SQLAlchemy 2.0** (async) + asyncpg, миграции **Alembic**
- **PostgreSQL 16**
- Фоновые задачи: **ARQ** + **Redis**. Форматирование и опрос антиплагиата не выполняются в HTTP-запросе.
- Работа с .docx: **python-docx** + **lxml** для низкоуровневых правок OOXML
- **LibreOffice headless**: подсчёт страниц, обновление содержания, конвертация в PDF для предпросмотра
- Хранение файлов: **MinIO** (S3-совместимое). В БД лежат только ключи объектов.
- Аутентификация: JWT (access + refresh), пароли через argon2
- Тесты: **pytest**, pytest-asyncio, httpx; линтер и форматтер **ruff**; типы **mypy**

**Frontend**
- **React 18 + TypeScript**, сборка **Vite**
- **TanStack Query** для серверного состояния, **React Router**
- UI: **Mantine** (или shadcn/ui; выбрать один и не смешивать)
- Формы: react-hook-form + zod
- API-клиент генерируется из OpenAPI FastAPI (`openapi-typescript`), типы вручную не дублируются
- Тесты: Vitest + Testing Library; линтер ESLint, форматтер Prettier

**Инфраструктура**
- **Docker Compose**: `backend`, `worker`, `frontend`, `postgres`, `redis`, `minio`
- Конфигурация через `.env` (pydantic-settings). Секреты не коммитятся; есть `.env.example`.

## Команды

```bash
# поднять всё окружение
docker compose up -d --build

# backend
cd backend
uv sync                                  # зависимости (менеджер пакетов uv)
uv run uvicorn app.main:app --reload
uv run arq app.worker.settings.WorkerSettings
uv run alembic revision --autogenerate -m "описание"
uv run alembic upgrade head
uv run pytest
uv run ruff check . && uv run ruff format . && uv run mypy app

# frontend
cd frontend
npm install
npm run dev
npm run gen:api                          # регенерация клиента из /openapi.json
npm run test
npm run lint
```

## Правила разработки

### Общие
- Код, идентификаторы и коммиты пишутся на английском; UI-тексты, комментарии к доменной логике и документация в `docs/` на русском.
- Роутеры тонкие: логика живёт в `services/`, доступ к БД только через сервисы.
- Любое изменение моделей сопровождается миграцией Alembic. Миграции после мержа не редактируются.
- После изменения API нужно перегенерировать фронтовый клиент.
- Новая функциональность покрывается тестами; для форматирования тесты обязательны.

### Файлы и версии
- **Загруженный исходник никогда не изменяется.** Форматирование создаёт новую `DocumentVersion` (или выходной файл `FormattingRun`) со ссылкой на исходную.
- Файлы хранятся в MinIO по ключу `departments/{dept_id}/theses/{thesis_id}/versions/{version_id}/{original|formatted}.docx`.
- Принимаются только .docx; проверяются MIME, размер (лимит в настройках) и то, что файл является корректным zip/OOXML.

### Автоформатирование
- Правила оформления задаются данными (`FormattingProfile`, JSON), а не константами в коде. Каждое правило — отдельный класс в `formatting/rules/` с методами `check()` и `apply()`.
- Каждое применённое изменение попадает в отчёт: что, где (раздел или абзац) и было/стало.
- Правило, которое не может безопасно исправить фрагмент, не трогает его и пишет предупреждение в отчёт. Портить содержимое ради оформления нельзя.
- Текст документа не меняется (кроме нумерации и подписей). Сравнение текста до и после входит в тесты.
- Для каждого правила есть фикстура «до» и ожидаемый результат в `tests/fixtures/docx/`.
- Список литературы оформляется по **ГОСТ Р 7.0.100-2018**. Источник, который не удалось распознать, помечается в отчёте, а не переписывается наугад.
- Подсчёт страниц и обновление содержания выполняются через LibreOffice headless в воркере.

### Антиплагиат
- Вся работа с API идёт через `integrations/antiplagiat/client.py`; в остальном коде прямых HTTP-вызовов нет.
- API ограничен, поэтому поддерживаемые возможности описаны в одном месте (`capabilities`). UI показывает только то, что реально доступно.
- Проверка асинхронная: задача в ARQ отправляет документ, затем опрашивает статус с backoff. Результат сохраняется в `PlagiarismCheck`.
- Учитываются лимиты API; повторная проверка той же версии (по хэшу) не отправляется без явного запроса.
- В тестах внешний API мокается (respx); реальные вызовы допускаются только в ручных интеграционных тестах с маркером `@pytest.mark.external`.

### ЭОС
- Интерфейс `EosAdapter` в `integrations/eos/base.py`; реализации `MockEosAdapter` (по умолчанию) и `RealEosAdapter` (после получения доступов).
- Реализация выбирается через `EOS_ADAPTER=mock|real` в `.env`.
- `MockEosAdapter` собирает комплект в zip, сохраняет его в хранилище и помечает выгрузку как выполненную в тестовом режиме.
- Остальная система про конкретную реализацию не знает.

### Безопасность и данные
- Персональные данные студентов не логируются. В логах только id.
- Авторизация проверяется на уровне объекта: студент видит только свою ВКР, руководитель только своих студентов, админ кафедры только свою кафедру.
- Ссылки на файлы выдаются как presigned URL с коротким сроком жизни.

## Связь с ВКР (пояснительной запиской)

Проект одновременно является предметом ВКР, поэтому:
- Архитектурные решения фиксируются кратко в `docs/adr/NNNN-название.md` (контекст, решение, альтернативы). Это пригодится для главы 2.
- Функциональные модели делаются в **IDEF0** (`docs/idef0/`).
- Требования к качеству соотносятся с характеристиками **ГОСТ Р ИСО/МЭК 25010-2015**. Тесты и метрики, которые это подтверждают, отмечаются в `docs/quality.md`.
- Стадии разработки соответствуют **ГОСТ Р 59793-2021**.
- Терминология обработки текста берётся из **ГОСТ Р ИСО/МЭК 2382-23-2004**.

## Чего не делать

- Не изменять исходные загруженные файлы.
- Не выполнять форматирование или запросы к антиплагиату синхронно в HTTP-обработчике.
- Не хардкодить этапы, сроки и правила оформления конкретной кафедры.
- Не обращаться к ЭОС напрямую в обход адаптера.
- Не коммитить `.env`, ключи API и реальные документы студентов (в фикстурах только синтетические тексты).
