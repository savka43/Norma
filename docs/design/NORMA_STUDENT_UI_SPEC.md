# Норма — спецификация компоновки студенческого интерфейса

Статус: согласованная концепция UI/UX, 27.11.2026. Назначение: контекст для Codex при реализации React-компонентов. Это не окончательная дизайн-система и не новая спецификация backend.

## 1. Инструкция Codex

Перед изменениями изучи AGENTS.md, существующие требования, маршруты, компоненты, API и дизайн-токены репозитория. Сохрани существующую архитектуру и функциональность. Реализуй описанную ниже компоновку, не придумывая новые страницы и бизнес-процессы. При конфликте с существующими требованиями явно обозначь его. Не заменяй работающий редактор или API демонстрационными заглушками. Если функциональность отсутствует, отдели UI от интеграции и сообщи об ограничениях.

Стек: React + TypeScript, CSS Modules, TanStack Form для форм. Без Tailwind, shadcn/ui и Tiptap. Используй текущие зависимости проекта; новые — только при обоснованной необходимости. Имена компонентов и маршруты ниже рекомендательные, адаптируй их к репозиторию.

## 2. Общие принципы

- Строгий светлый интерфейс, прямоугольные элементы, без декоративных скруглений, градиентов, избыточных теней и карточек ради карточек.
- Использовать существующую дизайн-систему. Визуальные правила определяются DESIGN_SYSTEM.md и tokens.css. Wireframe задаёт обязательные области, состав информации, иерархию и сценарии, но не точный внешний вид. Не копировать схему пиксель в пиксель.
- Не использовать большие приветственные баннеры, статистические плитки, графики ради заполнения пространства.
- Основной контент личного кабинета центрирован, ориентир максимальной ширины 1100–1200 px (не обязательное точное значение).
- Единая горизонтальная навигация, никакого глобального сайдбара.
- Один студент — одна ВКР; не создавать список проектов или промежуточный экран открытия документа.

StudentHeader: слева логотип «Норма», затем «Моя ВКР», «Редактор», «Проверки», «Материалы»; справа уведомления и профиль. Активный раздел обозначен ненавязчиво. - Полная доступная высота окна, собственная шапка и инструменты. Скролл документа независим от панелей.
- Центральная область — последовательность страниц А4 с автоматической пагинацией, а не набор независимых textarea. Сохранять требования к импорту DOCX, таблицам, изображениям, формулам, экспорту PDF/DOCX, заголовкам, оглавлению и нумерации. Правила оформления определяются существующей спецификацией ГОСТ и требованиями кафедры.
- Левая панель — сворачиваемое дерево структуры документа, сформированное из заголовков. Переход к разделу; индикаторы согласования глав.
- Справа постоянная узкая рейка инструментов: Правки, Материалы, История версий, Оформление. Клик открывает соответствующую панель, повторный клик закрывает. По умолчанию одна правая панель за раз; обе боковые панели можно скрыть. Не перекрывать текст панелью на широком экране.
- Правая панель материалов изменяемой ширины; при просмотре PDF две независимые прокручиваемые области. Не создавать дубликат полноценной страницы материалов.
- Нижняя строка: номер страницы, количество страниц/слов при наличии данных, профиль оформления, масштаб.

### 5.2. Меню и панель форматирования

Файл: импорт DOCX, экспорт PDF/DOCX. Правка: отмена/повтор, поиск и замена. Вставка: таблица, изображение, формула, разрыв страницы, ссылка. Формат: стили, абзацы, списки, параметры оформления. Вид: структура, правки, масштаб, горячие клавиши. Инструменты: история версий, проверка оформления. Панель форматирования: undo/redo, масштаб, стиль абзаца, шрифт/размер, начертание, выравнивание, интервалы и списки. Не дублировать все меню отдельными кнопками. Не разрешать форматирование, противоречащее установленным ограничениям документа, без предусмотренной доменной логики.

### 5.3. Режимы

| Элемент | Редактирование | Рецензирование | Сравнение версий |
|---|---|---|---|
| Редактирование текста | Да | Да | Нет |
| Форматирование | Да | Да | Нет, инструменты diff |
| Правки | По запросу | Открыты автоматически | Скрыты по умолчанию |
| Выделение предложений | Скрыто по умолчанию | Включено, можно скрыть | Diff версий |
| Материалы | Доступны | Доступны | Доступны |
| Структура | Доступна | Доступна | Доступна |

Переключатель режимов справа в toolbar, без отдельной постоянной строки. Сохранять позицию/главу, масштаб, состояние текста и предпочтения панелей по режимам. Перед сравнением обеспечить сохранность несохранённого черновика. Не смешивать diff сохранённых версий с предложениями руководителя.

Сравнение: выбор двух сохранённых версий с датами, отображение рядом (синхронная прокрутка по соответствующим блокам) или совмещённый diff; удалённое выделено красным фоном, добавленное зелёным; основной цвет текста сохраняется, зачёркивание запрещено; навигация предыдущая/следующая разница; возможность скрыть подсветку. При одинаковых версиях — «Изменений нет». Режим только для чтения.

### 5.4. Правки: комментарии и предложенные замены

Панель объединяет оба типа. Фильтры: все / комментарии / предложения, открытые / все. Элемент показывает автора, раздел, дату, текст, статус. Клик перемещает к привязанному фрагменту. В рецензировании есть переход к предыдущей/следующей правке.

Комментарий: руководитель выделяет фрагмент, оставляет замечание; студент исправляет текст, отвечает и отмечает исправленным; это не равно подтверждению руководителем.

Предложение: руководитель выделяет текст, выбирает «Предложить замену текста», вводит замену и необязательное пояснение. Исходник не меняется. Студент видит удаляемый и предлагаемый текст, принимает или отклоняет изменение, может обсуждать его. Принятие атомарно изменяет документ; отклонение сохраняет исходник; решение сохраняется в истории. Если исходный фрагмент изменён и предложение нельзя однозначно сопоставить, показать конфликт и запретить автоматическую замену. Не привязывать замечание исключительно к номеру страницы: пагинация меняется. Использовать стабильные идентификаторы блоков и привязку к диапазону/версии согласно модели редактора. Руководитель не редактирует студенческий документ напрямую. Принятие всех предложений не означает согласования главы.

### 5.5. Отправка на проверку

Кнопка в шапке открывает диалог выбора разделов (одного или нескольких) и необязательного комментария. Фиксируется отправленная версия. Статусы: не отправлено, на проверке, нужны правки, проверено успешно. Завершение — только по явному подтверждению руководителя. Повторная отправка формирует новую проверяемую версию. Реализовать ограничения согласно backend.

## 6. Проверки

```text
Проверки
Научный руководитель | Антиплагиат | Нормоконтроль
──────────────────────────────────────────────────────────────
Согласование разделов                        Принято 1 из 5
Раздел                    Статус           Обновлено  Замечания
Введение                  Принято          21.11      0       ›
1. Аналитическая часть    Нужны правки      26.11      3       ›
2. Проектирование         На проверке      27.11      —       ›
3. Реализация             Не отправлено    —          —       ›
Заключение                Не отправлено    —          —       ›
История отправок и проверок →
```

`ReviewsPage` → `ReviewTabs` → `SupervisorReviews`, `OriginalityReviews`, `FormattingReviews`. Без промежуточного обзорного экрана, по умолчанию вкладка руководителя.

- Руководитель: таблица разделов, статус, дата обновления, число замечаний. Раскрытие строки: отправленная версия, дата, комментарий руководителя, замечания, история, переход к конкретному фрагменту редактора. Исправление и отправка главы — в редакторе.
- Антиплагиат: последний результат (оригинальность, заимствования, цитирование только если доступны), версия, дата, отчёт, новая проверка и история. Уведомлять, если документ изменился после проверки. Тестовый API «Антиплагиат» — только искусственные документы; не отправлять реальные ВКР или персональные данные. Не выдавать тестовые проценты за реальные.
- Нормоконтроль: статус, нормоконтролёр, версия, список замечаний по оформлению с номерами страниц и статусами, переход к исправлению, повторная отправка и история. Вкладка доступна для просмотра всегда; отправка только после обязательных предшествующих этапов. Автоматическая проверка оформления в редакторе не заменяет подтверждение нормоконтролёра.

## 8. Состояния и доступность

Разделять серверное состояние (документ, версии, проверки, материалы) и локальное UI (режим, раскрытие панелей, фильтры, масштаб). Не создавать отдельные копии документа для каждого режима. Автосохранение: видимые состояния сохранения, сохранено, ошибка/нет связи; не показывать ложное подтверждение. Все списки и запросы предусматривают загрузку, пустое состояние, ошибку и повтор. Кнопки доступны с клавиатуры, иконки имеют accessible name и подсказки, диалоги управляют фокусом. Статусы различимы не только цветом. На узких экранах панели сворачиваются; приоритет — десктопный workspace. Конкретные адаптивные пороги не утверждены.

## 9. Авторизация, профиль и уведомления

Вход: тёмно-синяя шапка с названием, центральная белая форма с email, паролем, показом пароля, входом, восстановлением пароля и ссылкой на регистрацию студента. Регистрация: фамилия, имя, отчество (если применимо), группа, email, пароль, повтор пароля; без выбора привилегированной роли и без создания ВКР в форме. Сверить поля и восстановление пароля с текущим API. После регистрации без назначенной ВКР — объясняющее пустое состояние.

Меню профиля: имя/роль, группа, email, профиль, настройки, выход. Профиль: вкладки личных данных, безопасности (смена пароля), уведомлений; группа только для чтения. Настройки почтовых событий только при наличии серверной поддержки.

Уведомления: выпадающая панель из шапки, счётчик непрочитанных, фильтры все/непрочитанные, отметить все прочитанными, событие с датой и переходом к соответствующему объекту. Не создавать обязательную отдельную страницу.

## 10. Порядок реализации и критерии приёмки

1. Изучить репозиторий и составить краткий план соответствия существующих компонентов этой спецификации.
2. Разделить layouts и реализовать навигацию/главную.
3. Реализовать оболочку редактора и переключение панелей, не ломая модель документа.
4. Реализовать режимы, правки, материалы и историю; интегрировать с существующими API.
5. Реализовать проверки и библиотеку материалов.
6. Проверить типы, линтер, существующие тесты и основные сценарии в браузере (Playwright при наличии).

Проверяемые сценарии: вход в редактор напрямую из навигации; отсутствие глобальной шапки в редакторе; возврат в кабинет; сворачивание панелей; переключение режимов с сохранением черновика; переход по замечанию к фрагменту; принятие/отклонение/конфликт замены; просмотр материалов без выхода; сравнение версий только для чтения; отправка главы с фиксацией версии; невозможность преждевременного нормоконтроля; поиск материалов. Сверить компоновку с wireframe, а не только наличие компонентов.

Все имена, даты, числа страниц и тексты в схемах являются примерами. Не хардкодить их в продукте. Реализация конкретных алгоритмов пагинации, diff, привязок и форматов хранения должна соответствовать отдельной технической архитектуре редактора.
