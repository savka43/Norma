# ADR-008 — Группы руководителя и назначение зарегистрированных студентов

**Статус:** принято как техническое решение backend-части фазы 2. **Дата:** 2026-11-19.

## Контекст

После auth из ADR-007 реализуется UC-07/FR-07: руководитель формирует свои группы
из самостоятельно зарегистрированных студентов. Исходная ЛР2 задаёт название,
учебный год, дату создания группы и принадлежность студента одной группе.
Академическая группа студента — отдельное профильное поле, не эта связь.

## Решение

- `SupervisorGroup`: UUID, `supervisor_id`, название, `academic_year`, `created_at`.
  Владельцем становится текущий аутентифицированный руководитель; поле владельца
  не принимается из тела запроса. Руководитель может иметь несколько групп.
  Название — 1–255 символов после обрезки пробелов по краям. Уникальность названия
  или сочетания названия/года не вводится: такого бизнес-ограничения в ЛР нет.
- Техническая конкретизация учебного года: целое число начала учебного года,
  например `2026` для 2026/2027. Диапазон 1–9998 позволяет представить следующий
  год четырёхзначной календарной датой; текущим годом выбор не ограничен.
  Строки и boolean вместо числа не принимаются. Это формат API, не новое правило ЛР.
- Группа создаётся пустой, затем наполняется отдельными запросами. Это промежуточное
  состояние процесса формирования группы, а не отмена отношения «группа — студенты»
  из UML. Автоматическое создание ВКР при добавлении не выполняется: модель ВКР
  появится в фазе 3.
- `GroupMembership`: `student_id` как первичный ключ, `group_id`, `joined_at`.
  Уникальность `student_id` действует глобально, независимо от руководителя
  и учебного года. Без отдельного согласованного перехода повторное назначение
  не переносит студента и возвращает `409`, в том числе в ту же группу.
- Проверка свободности только перед записью была бы подвержена гонке. Здесь
  неизменность назначения обеспечивает уникальный ключ PostgreSQL: при конкурентных
  запросах один коммит проходит, второй получает именованный конфликт ключа,
  который сервис переводит в `409`. Другая ошибка БД не маскируется под этот конфликт.
- `OwnedGroupDep` объединяет проверку роли и запрос `id + supervisor_id`.
  Чужая и отсутствующая группа одинаково возвращают `404`; это не раскрывает
  существование чужих групп. Студент получает `403`, без сессии — `401`.
  Проверка выполняется при чтении группы, состава и добавлении студента.
  Создание/список групп и поиск студентов также требуют `SupervisorDep`.
- Для назначения выбирается только существующий `User(role=student)`;
  отсутствующий UUID и UUID руководителя возвращают одинаковый `404`.
  FK обеспечивают существование записей; соответствие роли проверяет backend.
  API изменения ролей отсутствует. Фильтр владельца и роль не полагаются на UI.
- Поиск `GET /students?query=...` предназначен для добавления: только студенты
  без группы, без руководителей и уже назначенных студентов. Состав своей группы
  доступен отдельным запросом; чужой состав не выводится через поиск.
  Поиск по подстроке ФИО/email без учёта регистра, от 3 до 100 символов после
  обрезки краёв. `%`, `_` и escape-символ рассматриваются буквально.
  Ответ содержит только UUID, ФИО, email и академическую группу; без хэша пароля,
  сведений о сессиях, руководителях и чужих назначениях.
- Списки возвращают `{items, limit, offset}` без полного справочника и отдельного
  подсчёта общего количества. Поиск: по умолчанию 20, максимум 50 записей;
  группы/состав: по умолчанию 50, максимум 100. `offset` — 0..2^63−1, границы
  PostgreSQL. Сортировка стабильная: группы — создание/UUID по убыванию;
  студенты — ФИО/UUID по возрастанию. Это технические ограничения выдачи.
- Права и CSRF наследуются из ADR-007; изменяющие запросы требуют
  `X-CSRF-Protection: 1`, чтение списков/состава использует `Cache-Control: no-store`.
- Миграция `0004_supervisor_groups` добавляет две таблицы, FK, CHECK и индексы.
  FK используют `RESTRICT`: прямое удаление связанных записей не должно молча
  уничтожать назначения. Пока нет API удаления/переноса; их правила необходимо
  согласовать с будущими ВКР и историей. Откат удаляет сначала участия, затем группы,
  сохраняя таблицы пользователей и сессий.

## Проверка и границы результата

API/DB-тесты проверяют формирование группы из самостоятельно зарегистрированного
студента, изоляцию двух руководителей, запрет студенту/гостю, валидацию, CSRF,
ограниченный поиск, состав, пагинацию и конфликты без перепривязки. Две проверки
используют реальные параллельные HTTP-запросы с независимыми сессиями/соединениями
PostgreSQL: назначение в одну группу и в группы разных руководителей.
Данные этих проверок искусственные и удаляются в `finally`; остальные используют
откат внешней тестовой транзакции. Проверяется полный цикл миграций и `alembic check`.

Это backend-покрытие UC-07/FR-07 и части EXT-06/NFR-01. Frontend и E2E не реализованы;
вся фаза 2 не объявляется завершённой. Работа с ВКР/этапами требует отдельной задачи
фазы 3, проверки прав на эти сущности здесь ещё нет.
