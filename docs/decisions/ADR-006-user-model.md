# ADR-006 — Общая учётная запись и две роли пользователя

**Статус:** принято как техническое решение части фазы 2. **Дата:** 2026-11-18.

## Контекст

Пользователь запросил модель пользователя с ролями и миграции БД. Исходные
атрибуты студента и руководителя перечислены в `docs/architecture/domain-model.md`.
Требуется общая идентичность для будущей аутентификации с сохранением двух
бизнес-ролей и их профильных данных. Регистрация, сессии, bootstrap и группы
не входят в эту задачу.

## Решение

- Одна ORM-модель `User` и таблица `users`: `id`, `email`, `full_name`,
  `password_hash`, `role`, `academic_group`, `position`, `department`, `created_at`.
  Отдельные таблицы профилей пока не нужны: роль одна, профильных полей три.
- `id` — UUID v4, генерируемый приложением при ORM-вставке. `created_at` —
  `TIMESTAMP WITH TIME ZONE`, заполняемый самой БД через `now()`.
- `UserRole` — строковый Python enum со значениями `student` и `supervisor`.
  В PostgreSQL используется native enum `user_role` с теми же строчными значениями.
  У роли нет значения по умолчанию: будущая регистрация должна явно назначать
  `student`, bootstrap — `supervisor`; публичный выбор роли не предусматривается.
  Для сохранения значений, а не имён членов Python enum, задан `values_callable`
  согласно [документации SQLAlchemy](https://docs.sqlalchemy.org/en/20/core/type_basics.html#sqlalchemy.types.Enum).
- Атрибуты ЛР сохранены непосредственно в `users`. Техническое уточнение
  обязательности: студенту требуется непустая `academic_group`, руководителю —
  непустые `position` и `department`. Поля другой роли должны быть `NULL`.
  `CHECK` с явными `IS NOT NULL` обеспечивает это и при прямой записи в БД.
  Академическая группа не заменяет будущую группу научного руководителя.
- Email уникален между всеми пользователями без учёта регистра: уникальный
  индекс `lower(email)`. Исходный регистр адреса сохраняется; пробелы по краям
  и пустая строка отвергаются. Будущий login должен искать по `lower(email)`.
  Проверка синтаксиса email и нормализация входных данных относятся к будущим
  API-схемам регистрации, а не считаются реализованными этим индексом.
- Лимиты хранения — технический выбор: email 254 символа, ФИО/должность/кафедра
  255, учебная группа 100. Это не требования ЛР. ФИО и `password_hash` не могут
  быть пустыми или состоять только из обычных пробелов.
- Для пароля есть только `password_hash TEXT`, без поля открытого пароля.
  Модель хранит уже подготовленный хэш; алгоритм хэширования и его безопасное
  применение будут реализованы в auth. Ограничение непустоты само по себе
  не проверяет криптографический формат. Новых HTTP-схем, сериализующих хэш, нет.
- Миграция `0002_users` следует за `0001_api_foundation` и содержит собственное
  описание схемы без импорта текущей ORM-модели. `downgrade` удаляет индекс,
  таблицу и затем enum: PostgreSQL enum имеет отдельный жизненный цикл,
  описанный в [документации SQLAlchemy](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#sqlalchemy.dialects.postgresql.ENUM).

## Проверка и границы результата

Тесты используют настоящую PostgreSQL и миграции, без `create_all`. Проверены
сохранение и повторное чтение обеих ролей, UUID/временная отметка, уникальность
email при вставке и изменении, недопустимые роли и ограничения профиля/полей.
Миграционные тесты проверяют состояние таблицы и enum после отката, повторное
применение и `alembic check`. Строки тестов откатываются внешней транзакцией;
полный откат схемы выполняется только на выделенной БД с суффиксом `_test`.
