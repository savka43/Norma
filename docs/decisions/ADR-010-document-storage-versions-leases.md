# ADR-010 — Рабочий документ, аренда редактирования и неизменяемые снимки

**Статус:** принято как backend-инкремент фазы 4.
**Дата:** 2026-11-20.

## Основание

ADR-001, ED-01/10/13 и NFR-01/02/03 требуют единого Lexical JSON,
сохранения с контролем ревизии, последовательного редактирования и истории.
Отправка этапа в фазе 6 должна проверять конкретный снимок. Для него нужна
также неизменяемая версия параметров оформления, а не ссылка на изменяемые настройки.

## Документ и права

- На ВКР приходится максимум один `Document`, что защищено уникальным FK.
  После создания ВКР студент явно вызывает `POST /theses/{thesis_id}/document`
  с доступным `template_version_id`; создаётся один пустой абзац, ревизия 1.
  GET ничего не создаёт, отсутствующий документ даёт `404`, повторный POST — `409`.
  Миграция не заполняет документы/шаблоны существующих ВКР искусственными данными.
- Чтение документа/версий доступно студенту своей ВКР и её руководителю.
  Редактирование, аренда, снимки и восстановление доступны только студенту своей
  ВКР; руководитель проверяет текст и оставляет замечания в будущей фазе 6.
  Чужие сущности скрыты за `404`; неподходящая роль — `403`, отсутствие сессии — `401`.
  Сессии/CSRF наследуются из ADR-007, ответы документов — `Cache-Control: no-store`.
- `Document` хранит JSONB, `schema_version`, отдельную от плана ВКР `revision`,
  выбранную версию шаблона, счётчик контрольных версий и даты.
  Сохранение меняет весь JSON атомарно, увеличивает ревизию на 1, в том числе
  при одинаковом содержимом. Автосохранение не создаёт контрольный снимок само.

## Схема Lexical v1

- Строгие Pydantic-схемы поддерживают `root`, `paragraph`, `heading` h1–h6,
  `quote`, `list` (`bullet|number`), `listitem`, `text`, `linebreak`, включая
  вложенные списки. Корень содержит хотя бы один блок; пустой абзац допустим.
- Прямое HTML-содержимое, неизвестные узлы/поля/версии и произвольный inline CSS
  дают `422`; ничего не удаляется молча. `style`/`textStyle` пока только пустые.
  Базовое выделение хранится как штатные флаги Lexical; внешний вид блоков
  должен определяться шаблоном в будущем frontend.
- Содержимое проходит технические ограничения: 2 MiB компактного UTF-8 JSON,
  50 000 объектов JSON, 64 уровня JSON, indent 0–100. Это ограничения выбранной
  реализации, не требования ЛР или лимиты внешнего сервиса. Проверяется JSON
  после HTTP-декодирования; ограничение сырого HTTP body до декодирования не реализовано.
  NUL и непарные Unicode-суррогаты отклоняются до PostgreSQL; также проверяются
  имена шаблонов и комментарии к версиям.
- API сохраняет поддержанный JSON и возвращает его без добавления отсутствовавших
  необязательных полей. Поддержка проверена экспортом и обратным чтением
  `@lexical/headless` **0.53.0** (headings/quote/inline formatting/linebreak/nested lists),
  Python-валидацией и HTTP/JSONB round-trip той же фикстуры.
  Версия библиотеки — версия проверочной фикстуры, не новая runtime-зависимость Python.
- Таблицы, изображения, подписи как custom nodes, ссылки, NodeState и остальные
  расширения пока не принимаются. Их поддержку нужно расширять проверяемой схемой
  при реализации frontend/импорта, не обходить валидатор произвольным JSON.
  Содержимое не делится на страницы, layout/A4 здесь не реализованы.

## Версии шаблона

- `FormattingTemplate` принадлежит руководителю; `FormattingTemplateVersion`
  содержит номер и неизменяемый JSON параметров. Руководитель создаёт шаблоны
  и новые версии только своих шаблонов. Студент читает шаблоны руководителя своей
  группы, свободный студент получает пустой список. Доступ к чужим UUID — `404`.
- Минимальная схема параметров: A4/orientation/margins, стили основного текста,
  шести уровней заголовков, подписей, списков и таблиц, начало нумерации страниц.
  Стили включают шрифт, размер, интервалы, отступ, выравнивание и выделение.
  Значения валидируются; отрицательные размеры, NaN/Infinity и CSS в имени шрифта
  не принимаются. При создании параметры задаются явно. ГОСТ-предустановка,
  проверки/исправления оформления, отображение и экспорт остаются фазами 4–5.
- Новый снимок шаблона требует `expected_version`, блокирует родительский шаблон
  и получает последовательный номер. Устаревший запрос — `409`.
  Документ может выбрать только версию шаблона своего руководителя.
  Старая версия остаётся доступной по UUID, новые параметры не переписывают историю.

## Аренда и конкурентность

- Любая мутация существующего документа сначала берёт `SELECT FOR UPDATE`
  строки `Document` и перечитывает ORM-объект. Это общий порядок блокировок для
  save/acquire/renew/release/snapshot/restore. Создание документа блокирует ВКР.
- Одна `DocumentEditLease` на документ: владелец, случайный UUID `lease_id`,
  время выдачи и истечения. Идентификатор возвращается только при выдаче/продлении,
  не входит в чтение документа; клиент передаёт его заголовком `X-Edit-Lease`.
  UUID различает редакторы одного пользователя, а роль/ownership проверяются отдельно.
- Получение при действующей аренде всегда даёт `409`, включая вторую вкладку
  того же студента. Продление требует текущей ещё действующей аренды.
  После истечения выдаётся новый UUID, старый не может сохранить, продлить или
  освободить новую аренду. Освобождение с правильным UUID допустимо и после
  истечения; отсутствие аренды при повторном DELETE — `204`.
- Время берётся из PostgreSQL `clock_timestamp()` после получения блокировки,
  а не из времени начала транзакции до ожидания. TTL задаёт
  `NORMA_DOCUMENT_LEASE_SECONDS`: по умолчанию 120, диапазон 30–3600 секунд.
  Продление — отдельный запрос, save не продлевает автоматически.
  Logout запрещает дальнейшие запросы с отозванной сессией; аренда без явного
  освобождения остаётся до TTL. Привязки аренды к конкретной cookie-сессии нет.
- Сохранение/снимок/восстановление проверяют также `expected_revision`.
  Конфликт ревизии/аренды — `409`, рабочее содержимое и история не меняются.
  При отсутствующем или невалидном `X-Edit-Lease` — `422` по схеме HTTP-запроса.

## Контрольные версии и восстановление

- `DocumentVersion` содержит полный снимок текста, версии схемы и шаблона,
  ревизию документа, автора, номер, комментарий и ссылку `restored_from_id`.
  Номер выдаётся под блокировкой документа. Создание снимка не меняет ревизию
  рабочего текста; две параллельные явные команды могут создать две версии
  одинакового текста с разными номерами, без перезаписи друг друга.
- `POST /documents/{id}/restore` принимает снимок **этого же** документа,
  заменяет рабочий текст/шаблон, увеличивает ревизию и создаёт новую версию
  со ссылкой на источник, всё в одной транзакции. Старые снимки не изменяются.
  Это явная замена рабочего состояния; неснятый в версию черновик автоматически
  не архивируется. Будущий UI должен учитывать это перед командой восстановления.
- API обновления/удаления контрольных версий и версий шаблонов отсутствует.
  PostgreSQL-триггеры дополнительно отвергают любой UPDATE обеих таблиц.
  FK `RESTRICT` защищают связанные снимки и цепочки восстановления.
  Регламент физического удаления оператором БД вне API пока не определяется;
  триггеры не являются защитой от владельца БД, который может их отключить.

## Проверки и оставшаяся работа

Миграция `0006_documents` создаёт пять таблиц и триггеры, откат удаляет также
функцию триггеров. Проверяются миграции/ORM, права, схемы, история/восстановление,
активная/истёкшая аренда, старый клиент, конфликт ревизий и неизменность БД.
Шесть тестов с независимыми соединениями проверяют конкурентные создание документа,
выдачу аренды, save, создание снимков, save/restore и новую версию шаблона.

Это backend-часть ED-01/10/13 и предпосылка UC-06/FR-06, не завершение всей фазы 4.
Frontend/A4, локальный несинхронизированный текст, diff, DOCX/PDF, комментарии,
контроль разрешённых областей во время проверки и переходы этапа не реализованы.
Отправка/решения остаются фазой 6, импорт/экспорт — фазой 5.
