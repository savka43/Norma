# ADR-007 — Регистрация, серверные сессии и bootstrap руководителя

**Статус:** принято как техническое решение backend-части фазы 2. **Дата:** 2026-11-19.

## Контекст

Модель пользователя уже реализована в ADR-006. Для EXT-06 и дальнейшего UC-07
нужны самостоятельная регистрация студента, вход/выход, определение текущего
пользователя и первоначальное создание руководителя. Бизнес-ролей по-прежнему две.
Требования оставляли выбор сессий и bootstrap технической задачей реализации.

## Решение

- `POST /api/v1/auth/register` всегда создаёт `student`. Неизвестные поля, включая
  `role`, `password_hash`, `position`, отвергаются, а не игнорируются. Email
  проверяется `EmailStr`, ФИО и профиль обрезаются по краям и не могут быть пустыми.
  Пароль не обрезается и не нормализуется. Технический диапазон нового пароля —
  12–128 символов, не требование ЛР. Регистрация возвращает профиль без входа.
- Пароли хэшируются Argon2id через `pwdlib[argon2]` с солью и текущими параметрами
  `PasswordHash.recommended()`. При успешном входе устаревшие параметры хэша
  обновляются через `verify_and_update`. Хэширование и проверка выполняются
  в thread pool, чтобы не блокировать async event loop. Подход с `pwdlib`/Argon2
  основан на [документации FastAPI](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/).
  JWT из примера не используется: здесь нужен немедленный серверный отзыв сессии.
- `POST /auth/login` ищет email без учёта регистра. Неизвестный email тоже
  проходит одну проверку пароля по фиктивному хэшу; ответ для неверного email
  и пароля одинаков: `401 Invalid email or password`. Уникальность email остаётся
  ограничением БД; конкурентный конфликт именованного индекса переводится в `409`.
- Клиент получает непрозрачный случайный токен из 32 случайных байт в host-only
  cookie `norma_session`: `HttpOnly`, `SameSite=Lax`, `Path=/api/v1`, `Max-Age`.
  В таблице `auth_sessions` хранится только SHA-256 токена, идентификатор пользователя,
  время создания и абсолютное истечение. Высокая энтропия токена позволяет
  использовать быстрый SHA-256; для паролей он не применяется.
  Настройка `NORMA_SESSION_LIFETIME_SECONDS` — 28800 по умолчанию (8 часов),
  допустимо 60–2592000 секунд. Продление при чтении отсутствует.
- `NORMA_SESSION_COOKIE_SECURE=false` позволяет локальный HTTP; при HTTPS требуется
  `true`. Параметры установки и удаления cookie следуют
  [API Starlette](https://starlette.dev/responses/#set-cookie).
  Сессионный токен не возвращается в JSON, профиль не содержит пароль/хэш;
  login/me/logout возвращают `Cache-Control: no-store`.
- При повторном успешном входе cookie заменяется и предыдущая сессия этого
  клиента отзывается в той же транзакции. Ошибка входа текущую сессию не отзывает.
  Другие браузеры имеют независимые сессии. `logout` удаляет запись и cookie,
  повторный выход и выход с неизвестным токеном возвращают `204`.
  `me` проверяет срок на сервере, а не полагается на истечение cookie.
- Защита от CSRF: все изменяющие auth-запросы и будущие изменяющие запросы через
  `CurrentUserDep` требуют `X-CSRF-Protection: 1`. Браузерный междоменный запрос
  с этим заголовком требует preflight; CORS-разрешений в API нет. Обычная форма
  без заголовка получает `403`, в том числе на login/logout. Это выбранный
  [OWASP-подход с custom request header](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#employing-custom-request-headers-for-ajaxapi).
  Frontend должен обращаться через тот же origin, в разработке — через Vite proxy.
  Добавление CORS потребует отдельной проверки политики доверенных origin.
- `CurrentUserDep` возвращает только пользователя действующей сессии;
  `SupervisorDep` дополнительно проверяет роль. Это основа NFR-01: проверка
  принадлежности конкретных групп/ВКР появится вместе с соответствующими моделями.
- `python -m app.bootstrap` создаёт руководителя через тот же валидатор и
  хэшер. Пароль вводится дважды через `getpass`, не передаётся аргументом команды.
  Повторный email даёт ошибку: команда не меняет пароль, профиль или роль
  существующего пользователя. HTTP-регистрации руководителя и третьей роли нет.
- Ошибки HTTP-валидации содержат только `loc`, `msg`, `type`; поля `input`, `ctx`
  исключены, чтобы не отражать пароль в ответе. CLI также не выводит входные значения
  при ошибке валидации. Секреты во входных Pydantic-схемах представлены `SecretStr`.
- Миграция `0003_auth_sessions` добавляет только таблицу сессий, FK с `ON DELETE
  CASCADE`, индекс пользователя и CHECK времени/формата хэша. Откат до `0002_users`
  удаляет сессии, сохраняя пользователей.

## Проверка и ограничения

API/DB-тесты выполняются на мигрированной PostgreSQL с откатом тестовых данных.
Проверяются публичная регистрация, ограничения входа, дубликаты, хэширование,
cookie, отзыв/ротация/истечение, независимые клиенты, bootstrap и проверка роли.
Миграционный тест проверяет upgrade/check/downgrade и повторное применение.

Автоматическая очистка истёкших записей, ограничение частоты запросов, подтверждение
email, восстановление пароля и управление устройствами пока не реализованы.
Истёкшая запись не даёт доступа, даже пока остаётся в БД. Эти ограничения не
позволяют объявить auth подготовленным для публичной production-эксплуатации.
Группы, предметные права и frontend пока остаются следующими задачами фазы 2.
