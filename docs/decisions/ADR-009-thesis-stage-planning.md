# ADR-009 — ВКР, настройка обязательных этапов и сводка прогресса

**Статус:** принято как техническая реализация первого backend-инкремента фазы 3.
**Дата:** 2026-11-20.

## Основание и границы

UC-08/FR-08 требуют настройки этапов, порядка и индивидуальных сроков,
UC-12/FR-12 — контроля прогресса и просрочек. Сохраняются два актёра,
одна ВКР на студента, все этапы обязательны, подтверждение только явным
действием руководителя. Решения пользователя из ADR-004 не изменяются.

В фазе 3 ещё нет `DocumentVersion`. Поэтому этот инкремент **не предоставляет**
отправку, возврат и подтверждение через API: отправка без неизменяемого снимка
нарушила бы UC-05. Enum состояний хранится в БД, новые этапы всегда `in_progress`;
машина переходов и история решений появятся вместе с workflow фазы 6.
Текущая `StageEvent` — история **настройки плана**, не история проверки документа.

## Создание и доступ

- Руководитель явно создаёт ВКР зарегистрированному студенту своей группы.
  Добавление в группу само по себе ВКР не создаёт. Роль и назначение проверяются
  backend; чужой, свободный, отсутствующий студент и UUID руководителя дают `404`.
- `Thesis.student_id` — уникальный FK на назначение `group_memberships.student_id`;
  `supervisor_id` берётся из сессии. Уникальность защищает и параллельное создание
  (`201` и `409`). FK с `RESTRICT` не допускают удаления участия с потерей связи.
  Соответствие руководителя владельцу группы проверяет сервис; прямой SQL-перенос
  участников не является поддерживаемой операцией.
- Студент читает свою ВКР, этапы и историю настройки, руководитель — только свои.
  Чужая и отсутствующая сущность одинаково дают `404`. Настройка и групповая сводка
  требуют роли руководителя. CSRF и cookie-сессии — по ADR-007, GET — `no-store`.
- Тема, дата начала и общий срок задаются при создании ВКР. Отдельный общий статус
  ВКР пока не вводится: текущий прогресс вычисляется по состояниям этапов.
  Изменение метаданных ВКР и удаление сущностей не входят в этот инкремент.

## Настройка плана и конкурентность

- `POST /theses/{thesis_id}/stages` добавляет этап в позицию `1..N+1`;
  `PATCH /stages/{stage_id}` принимает имя, позицию `1..N` и срок целевого этапа.
  В обоих запросах все эти поля и `expected_revision` обязательны.
  Остальные позиции сдвигаются атомарно, UUID этапов сохраняются.
- Техническая проверка сроков: начало ВКР ≤ срок этапа ≤ общий срок ВКР,
  общий срок ≥ начало. Порядок этапов не навязывает порядок дат.
  Неизвестные поля запрещены; статус, веса и необязательность передавать нельзя.
- `Thesis.revision` начинается с 1; одна фактическая правка плана увеличивает её
  на 1. Неизменяющий PATCH с актуальной ревизией не создаёт событие.
  Каждый writer сначала получает `SELECT FOR UPDATE` родительской ВКР,
  перечитывает её ревизию и этапы, затем проверяет `expected_revision`.
  Устаревший запрос получает `409` без изменения плана и истории.
  `populate_existing` обновляет уже загруженные ORM-объекты после ожидания блокировки.
- Чтение ВКР/плана/сводки удерживает shared-блокировку выбранных ВКР до загрузки
  этапов: состав плана и его ревизия не смешиваются с конкурентным сохранением.
  Групповая сводка загружает страницу студентов, их ВКР и этапы пакетно.
- Уникальность `(thesis_id, position)` отложена до commit, чтобы перестановка
  не давала ложный конфликт промежуточных позиций; положительность позиции — CHECK.
- Минимальное ограничение текущей настройки: если хотя бы один этап `in_review`
  или `completed`, изменение всего плана даёт `409`, в том числе добавление этапа.
  Так настройка не меняет проверяемый план или знаменатель прогресса после
  подтверждения. При состояниях `in_progress`/`changes_requested` настройка разрешена.
  Более гибкое изменение частично подтверждённого плана требует отдельной задачи;
  оно не включено молча в текущий API. Удаления этапов нет.

## История и расчёт

- `StageEvent` хранит актёра, ревизию ВКР, время и снимки `before`/`after`
  (имя, позиция, срок, статус). При создании `before` — SQL NULL.
  Перестановка пишет события для **всех** изменивших позицию этапов.
  События записываются в одной транзакции с планом; API изменения/удаления истории нет.
  FK запрещают удаление этапа с существующей историей. Это не защита от владельца
  БД с правами на прямое изменение SQL; как и остальные сущности, данные изменяет API.
- Прогресс = `100 * completed / total`, без весов; при нуле этапов — `null`,
  отдельно возвращается `total_stages=0`. Такой черновик не означает готовый план.
  Проверка ненулевого набора при отправке будет в фазе 6.
- Срок — календарная дата, действует включительно. Техническая точка отсчёта —
  текущая дата UTC, явно возвращаемая как `as_of_date`. Настройки часового пояса
  организации пока нет. Просрочен этап с `due_date < as_of_date`, кроме `completed`;
  нахождение на проверке не отменяет просрочку. ВКР просрочена после общего срока,
  пока не завершены все этапы; пустой план также не считается завершением.
- Сводка включает студентов без ВКР (`thesis: null`, `stages: []`) и без этапов.
  Пагинация студентов/ВКР/истории — по ADR-008 (50 по умолчанию, максимум 100).
  План одной ВКР возвращается целиком с ревизией, чтобы клиент мог менять порядок.
  Большие планы и ограничения их размеров отдельно не исследовались.

## Проверка

API/DB-тесты на PostgreSQL проверяют права обоих актёров, чужой доступ, валидацию,
CSRF, порядок и сохранение UUID, снимки истории, устаревшие запросы, сводку и
пагинацию. Три теста используют независимые соединения и реальные параллельные
HTTP-запросы: создание ВКР, добавление этапа, правка этапа. Проверяются ровно один
успешный ответ, один `409`, состояние победителя и отсутствие лишнего события.
Unit-тесты проверяют формулу прогресса и границу включительного срока.
Миграция `0005_theses_stages` проверяется через downgrade/upgrade и `alembic check`,
включая удаление enum при откате. Frontend и E2E пока отсутствуют.

Технические источники:
[SQLAlchemy: populate_existing](https://docs.sqlalchemy.org/en/20/orm/queryguide/api.html#populate-existing),
[SQLAlchemy: constraints](https://docs.sqlalchemy.org/en/20/core/constraints.html).
