# ADR-013 — Проверка этапов, замечания и сравнение версий

**Статус:** принято как техническая реализация backend фазы 6.
**Дата:** 2026-11-23.

## Основание

UC-04–06/09–11, FR-04–06/09–11, ED-11/12/14 и ADR-004 требуют отправки
фиксированной версии, явного решения руководителя, сохранения замечаний и истории.
Бизнес-роли и правила переходов не меняются. Frontend и E2E этой задачей не реализуются.

## Контрольная версия и переходы

- Студент отправляет этап из `in_progress` или `changes_requested`. Backend
  создаёт новый `DocumentVersion` из сохранённого рабочего JSON и выбранной версии
  шаблона, `StageSubmission` и событие `submitted` в одной транзакции.
  Предварительный отдельный запрос создания версии не требуется. Несохранённый
  локальный текст не включается: клиент сначала сохраняет его, затем передаёт
  актуальные `expected_document_revision`, `expected_revision` ВКР и edit lease.
- `ThesisStage.submitted_version_id` хранит последнюю отправленную версию;
  неизменяемые отправки сохраняют предыдущие связи. Руководитель читает этот
  снимок обычным защищённым API версий и может экспортировать его.
- Только руководитель делает `in_review → changes_requested/completed`.
  Идентификатор проверяемой версии обязателен в решении наряду с ревизией ВКР:
  старый экран проверки не может подтвердить следующую отправку.
  Замечание/пояснение к решению необязательно. Закрытие замечаний само по себе
  не подтверждает этап, открытые замечания не заменяют явного решения.
- Студент может отдельно выполнить `changes_requested → in_progress` (`resume`)
  либо сразу повторно отправить исправления. `completed` терминален в API.
  Прогресс по-прежнему равен `completed / all × 100%`, без весов.
- Каждая отправка/решение увеличивает `Thesis.revision`. Общая `StageEvent`
  расширяет аудит настройки: `submitted|changes_requested|confirmed|resumed`,
  снимки до/после, актёр, версия и необязательное пояснение. Существующие события
  не переписаны. UPDATE событий/отправок запрещён триггером PostgreSQL.
  Откат миграции с существующими отправками/замечаниями/решениями отвергается.

## Область проверки и конкурентность

В текущей схеме Lexical нет сопоставления областей документа этапам. Минимальная
проверяемая реализация отправляет **весь документ**. Пока хотя бы один этап
`in_review`, нет разрешённых для правки областей: save, restore, import и
apply-formatting возвращают `409`. Читать, экспортировать и создавать отдельные
снимки можно. После возврата всех проверяемых этапов либо завершения проверок
документ снова доступен для правок. Завершённые этапы сохраняют свои снимки.
Несколько этапов могут находиться на проверке одновременно.

Это явное ограничение первого backend workflow: редактирование других глав при
проверке одной главы требует отдельной модели областей и проверки их идентичности.
Такая модель не имитируется индексами блоков; её здесь нет. ED-14 частично покрыт
на уровне backend, полная готовность редактора не объявляется.

Writers плана и workflow сначала блокируют ВКР, затем workflow блокирует документ.
Document writers блокируют документ и читают статусы без дополнительного lock ВКР.
Проверка статусов выполняется после получения блокировки документа; submit/decision
меняют статус только удерживая тот же lock. Поэтому конкурирующие отправка и
замена текста не могут одновременно успешно использовать одну старую ревизию.
После ожидания блокировок ORM-состояние перечитывается (`populate_existing`).
Комментарии блокируют только собственную строку; разрешение использует
`expected_revision`. Проигравшие операции дают `409` без лишних снимков/событий.

## Замечания и привязки

`Comment` хранит версию, автора-руководителя, текст, исходную цитату, anchor,
`open|resolved` и ревизию. Студент и руководитель этой ВКР могут явно закрыть
замечание. Повторное закрытие даёт `409`; повторное открытие/редактирование/удаление
источника не добавляются. `CommentEvent` сохраняет создание и закрытие с актёром.
Триггер защищает источник замечания и разрешает только `open → resolved` с +1
ревизией; события неизменяемы. FK истории используют `RESTRICT`.

Anchor — `{block_id, offset_start, offset_end}`. `block_id` — путь по индексам
`children` **внутри неизменяемой версии**, например `0` для абзаца или `3/0/0/0`
для абзаца ячейки таблицы. Это не глобальный UUID и не устойчивый ID рабочего
Lexical-узла. Узлы v1/v2/v3 не мигрируются и их исходные JSON не меняются.
Семантические блоки: paragraph/heading/quote/caption/listitem, в том числе в
таблицах и вложенных списках. Диапазон относится к тексту одного блока; offsets
в единицах UTF-16, как в JavaScript/Lexical. Linebreak — `\n`, изображение — U+FFFC.
При создании backend проверяет полное совпадение цитаты с диапазоном; неверный
путь, выход за границы и разрезание surrogate pair дают `422`.

`anchor` и `quote` не меняются. `current_anchor` и `is_detached` вычисляются для
текущего рабочего документа: неизменившийся исходный блок сохраняет привязку;
иначе единственное точное совпадение цитаты может быть найдено на другой позиции.
Отсутствие или неоднозначность совпадений дают detached и неактивную ссылку.
Это best-effort, не гарантированная идентичность фрагмента при любых перестановках.
По умолчанию список скрывает resolved и detached; оба вида доступны отдельными
флагами, а исходная версия/цитата/история — всегда по правам. Фильтрация detached
идёт перед пагинацией видимых элементов, строки читаются порциями по 100.

## Diff

Любые две версии **одного документа** сравниваются без записи в БД. В ответе
идентификаторы версий, изменения схемы/шаблона/свойств root и последовательность
`equal|added|removed|changed`. Блок содержит путь, тип, текст и полный исходный
JSON; таблицы, изображения, вложенные списки и изменения форматирования не теряются.
Текстовые фрагменты содержат `before`/`after` для подсветки, включая удалённый текст.
Перемещения представлены удалением и добавлением, `move_detection=not_performed`.

Сопоставление top-level блоков использует SHA-256 канонического JSON и
`SequenceMatcher(autojunk=False)`. Лимит произведения числа блоков — 2 000 000,
при превышении `422`. Общий бюджет посимвольного сопоставления — 1 000 000 пар;
для более крупных изменений возвращается целый changed-фрагмент без усечения.
Вычисление diff вынесено из event loop в threadpool. Это детерминированный diff,
не полноценное распознавание семантических переносов или pixel-perfect Word diff.

## Проверки и границы

API/DB-тесты проверяют полный цикл с повторной отправкой, оба пути после возврата,
подтверждение без обязательного замечания, несколько проверок, права/CSRF,
ревизии/lease, запрет всех путей замены текста и неизменность истории PostgreSQL.
Независимые соединения проверяют submit/submit, submit/save/import/restore/format,
конкурирующие решения и закрытие замечания. Unit-тесты проверяют UTF-16,
таблицы/списки/изображения, удалённый текст, перемещения и бюджеты diff.
Frontend, реальное выделение Lexical и браузерные E2E ещё отсутствуют.
