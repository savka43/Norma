# ADR-005 — Основа API, конфигурация, healthcheck и миграции

**Статус:** принято как техническое решение фазы 1. **Дата:** 2026-11-17.

## Контекст

Пользователь выбрал начало разработки с API. Нужна запускаемая backend-основа
утверждённого стека без преждевременного добавления предметных сущностей.
Требуются воспроизводимость запуска и проверки на настоящей PostgreSQL
(подготовка NFR-05/07/08).

## Решение

- Используем Python 3.12, `uv` и lock-файл; FastAPI, SQLAlchemy 2.0 async,
  `asyncpg`, Alembic и Pydantic Settings. Backend находится в `backend/`,
  маршруты — в `app/api_v1/<feature>/`, ORM-модели — в `app/core/models/`.
- Пароль обязателен, загружается из окружения/неотслеживаемой `.env`, представлен
  `SecretStr`. URL создаётся через `sqlalchemy.URL.create`, что сохраняет
  специальные символы без ручной сборки DSN и экранирования пароля.
- Фабрика приложения принимает настройки для изолированных тестов. Engine
  создаётся на время lifespan и освобождается при остановке; на запрос выделяется
  отдельная async-сессия. Коммит остаётся явной обязанностью будущих операций записи.
  Механизм следует [документации FastAPI о lifespan](https://fastapi.tiangolo.com/advanced/events/)
  и [документации SQLAlchemy об async-сессиях](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html).
- `GET /api/v1/health` проверяет процесс без подключения к БД.
  `GET /api/v1/health/ready` выполняет `SELECT 1`; ошибка подключения или таймаут
  дают `503` с общим сообщением. Обрабатываются также прямые `PostgresError`
  драйвера: реальный тест неверного пароля показал, что SQLAlchemy не оборачивает
  эту ошибку подключения. Лимиты подключения и readiness настраиваются,
  значения по умолчанию — 5 и 3 секунды соответственно. Эти маршруты публичны
  и не возвращают предметные данные или параметры подключения.
- Alembic использует те же настройки и метаданные, online-миграции — async engine
  с `NullPool`, согласно [официальному cookbook](https://alembic.sqlalchemy.org/en/latest/cookbook.html#using-asyncio-with-alembic).
  Начальная ревизия `0001_api_foundation` не создаёт предметных таблиц: это
  техническая точка отсчёта. Таблицы появляются с задачами соответствующих фаз.
- В Compose PostgreSQL 16 имеет постоянный volume. Одноразовый `migrate`
  выполняется перед стартом backend, после готовности БД. Backend работает
  непривилегированным пользователем, локальные порты привязаны к `127.0.0.1`.
- Unit/API-тесты не требуют БД; интеграционные включаются явно и допускают
  только базу с суффиксом `_test`, поскольку проверяют также откат миграций.

## Границы результата

Это основа API фазы 1; бизнес-UC ещё не реализованы. Аутентификация, группы,
ВКР и последующие модули вводятся по roadmap. Выбор auth/cookie и bootstrap
руководителя документируется отдельно в фазе 2. Frontend-часть фазы 1 остаётся
невыполненной до её реализации и проверки.
