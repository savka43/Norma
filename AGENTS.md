# AGENTS.md — правила работы Codex над системой сопровождения ВКР

## Единственный действующий план

Все агенты работают только по `docs/plans/roadmap.md` и связанным с ним актуальным
требованиям, архитектуре и ADR из `docs/`, перечисленным ниже. `AGENTS.md` задаёт
общие правила работы. Не поддерживай параллельный план для Claude или другого агента.
Корневые `PLAN.md` и `CLAUDE.md` — только указатели на эти источники.

`docs/archive/` содержит устаревшие материалы исключительно для истории. Не читай
их как рабочие инструкции и не переноси из них роли, функции, зависимости или этапы.
Возвращаться к архиву можно только по явному запросу пользователя.

## Сначала прочитай, затем реализуй

Разрабатывается **полноценная** информационная система сопровождения этапов ВКР. Код может пока отсутствовать: это нормально, репозиторий начинается со спецификации. Не создавай отдельный throwaway-прототип перед разработкой продукта. Реализуй страницы A4 и нормализацию DOCX как части продукта, проверяя сложные места тестами.

Исходные требования выведены из двух лабораторных: ЛР №1 Business Use Case (12 UC), ЛР №2 UML (9 классов, 10 отношений). Оригиналы DOCX намеренно **не включены в репозиторий**. Читай рабочие извлечения:
- `docs/requirements/product.md` — требования, принятые решения, правила этапов;
- `docs/requirements/use-cases.md` — 12 сценариев и приёмка;
- `docs/requirements/editor.md` — обязательное поведение редактора;
- `docs/architecture/domain-model.md` — исходные классы и схема;
- `docs/architecture/overview.md`, `docs/architecture/editor-design.md`, `docs/architecture/api-contract.md` — реализация;
- `docs/decisions/` — принятые архитектурные решения;
- `docs/plans/roadmap.md` — очередность задач.

При противоречии: явно принятое решение пользователя > прежнее техническое предположение; требования ЛР остаются источником предметной области. Не меняй бизнес-смысл ЛР молча. Не изобретай недостающие детали; для узких технических неопределённостей выбирай минимальную проверяемую реализацию и отмечай выбор в ADR.

## Стек и организация кода

- Backend: Python + FastAPI + SQLAlchemy 2 async + Alembic + PostgreSQL + Pydantic.
- Один **модульный монолит**, `app/api_v1/<feature>/`: `views.py`, `schemas.py`, `crud.py`, `dependencies.py`, `service.py` при наличии сложных правил. SQLAlchemy-модели в `app/core/models/`. Не вводить Repository layer, CQRS и микросервисы без задачи.
- Frontend: React + TypeScript + Vite + React Router + TanStack Query + **TanStack Form** + **Lexical (`lexical`, `@lexical/react`)**.
- Стили: **CSS Modules** `Component.module.css` рядом с компонентом; `globals.css` только для reset, базовой типографики и дизайн-токенов. Свои компоненты в `shared/ui/`.
- **Не использовать Tiptap, Tailwind CSS, shadcn/ui, React Hook Form, Zod** (добавление любого из них потребует нового решения).
- Правила редактора — в `docs/requirements/editor.md`, технический дизайн — `docs/architecture/editor-design.md`. JSON-состояние Lexical — содержимое документа; страницы A4 — результат компоновки, НЕ отдельные источники текста.
- Текст оформляется преимущественно **семантическими стилями**: «Основной текст», «Заголовок», «Подпись», «Список», «Таблица». Шаблон определяет реальные размеры/отступы; не делай свободный toolbar с произвольными font-size/color как основу продукта.
- Нет одновременного редактирования, Yjs/CRDT, WebSocket, AI/ML-корректора страниц. Есть история, diff, comment anchors, lease/ревизии, импорт DOCX, экспорт DOCX/PDF.
- Две бизнес-роли: **студент и научный руководитель** (он управляет своими группами). Не добавляй нормоконтролёра, заведующего кафедрой или универсального администратора как третьего актёра.

## Навыки для frontend

Визуальный источник для интерфейса — пакет NORMA v0.1 в `docs/design/`.
Состав экранов сверяется с доступными действиями API и бизнес-правилами ниже.

Навыки установлены в проекте: общие файлы находятся в `.agents/skills/` для Codex,
а `.claude/skills/` содержит ссылки на те же навыки для Claude Code.
Папки `.agents/`, `.codex/` и `.claude/` локальные и не коммитятся.
Навыки устанавливаются отдельно от клонирования репозитория; при необходимости восстанови ссылки
из `.claude/skills/` на соответствующие навыки в `.agents/skills/`.
Перед соответствующей задачей читай нужный `SKILL.md`:

- `frontend-design` — `.agents/skills/frontend-design/SKILL.md`: создание и изменение интерфейса, визуальная композиция и стили.
- `web-design-guidelines` — `.agents/skills/web-design-guidelines/SKILL.md`: ревью интерфейса, доступности и удобства использования.
- `webapp-testing` — `.agents/skills/webapp-testing/SKILL.md`: проверка работающего приложения в браузере, сценарии Playwright, снимки экрана и диагностика.

Навыки помогают выполнять текущую фазу roadmap; они не меняют требования продукта
или утверждённый стек. Примеры из навыков адаптируй к CSS Modules, TanStack Form
и собственным UI-компонентам. Не добавляй запрещённые библиотеки по примеру из навыка.

## Бизнес-правила — не менять

- Студент регистрируется сам; руководитель добавляет зарегистрированного студента в свою группу.
- Руководитель создаёт все обязательные этапы и сроки, подтверждает каждый этап **явным действием**.
- Статусы этапа: `in_progress` → `in_review` → `changes_requested` или `completed`; после правок `changes_requested` → `in_review`. По отдельному действию допускается возврат `changes_requested` → `in_progress` без потери истории. `completed` — терминальное состояние в обычном потоке.
- Прогресс = подтверждённые этапы / все этапы * 100%; ненулевой набор этапов обязателен для отправки на проверку. Не использовать веса.
- Отправка этапа всегда фиксирует **неизменяемую версию документа**, которую проверяет руководитель. Во время проверки сам этап нельзя редактировать; рабочий текст можно править в разрешённых областях при сохранении идентичности контрольной версии.
- Замечания сохраняются вместе с исходным фрагментом/версией, закрытые скрываются по умолчанию и могут быть показаны в истории; удалённый/перемещённый текст доступен при сравнении версий.
- Антиплагиат: официальный **тестовый** SOAP API, проверка фиксированной версии в долговечном background workflow с хранением результата. Урезанная база достаточна для демонстрации. Без автоматического повторного внешнего запроса после ошибки.
- Оформление: шаблон по умолчанию ориентирован на ГОСТ 7.32-2017; все проверки/исправления используют **выбранные настраиваемые параметры шаблона**, а не захардкоженные значения.

## Порядок выполнения задач

1. **Research**: прочитай релевантные документы и код; обнаружь реальные неизвестные.
2. **Propose**: коротко сформулируй решение; для редактора не обещай эквивалентность Word без проверки.
3. **Plan**: перечисли файлы, тесты и критерии приёмки.
4. **Implement**: реализуй согласованную вертикальную задачу, без незапрошенных функций.
5. **Test**: запусти доступные тесты, линтеры и сборку; явно укажи что не удалось проверить.

Пользователь хочет **работающий продукт**, а не бесконечную фазу анализа. Если задача на реализацию, не останавливайся после плана и не требуй одобрения каждого тривиального технического решения. Следуй `docs/plans/roadmap.md`; делай функциональность инкрементально и не переходи к следующей большой фазе без запроса.

### Фиксация прогресса

- Перед каждой задачей читай «Текущий статус» и последние записи «Журнала выполнения»
  в `docs/plans/roadmap.md`, затем проверяй соответствующий код.
- После каждой задачи обновляй эти разделы: фактически выполненное, покрытые
  UC/FR/ED/NFR, основные изменённые файлы, команды проверок и результаты,
  непроверенные части, ограничения и ближайший шаг. Итог в чате не заменяет запись.
- Различай готовность backend, frontend и всей фазы; частичное выполнение отмечай
  явно. Не отмечай завершение без проверки критериев приёмки.
- Обоснования технических решений фиксируй в `docs/decisions/`, инструкции запуска —
  в `docs/development.md`. По решению пользователя `README.md` содержит только
  картинку; не добавляй туда текст. Не заводи параллельный план или отдельный
  контекст для другого агента.

## Качество и безопасность

- Python: type hints, Ruff, BasedPyright, pytest; миграции Alembic.
- Frontend: TypeScript strict, ESLint, Prettier, Vitest + Testing Library; сквозные сценарии Playwright.
- Права на каждую ВКР/группу проверяются **backend**, не только в UI; пароль в БД — хэш.
- `DocumentVersion` и результаты проверки не изменяются задним числом; конкурентные сохранения дают `409`.
- Импорт DOCX: недоверенный файл, ограничения объёма, проверка ZIP, санитизация HTML и сохранение исходника отдельно; не рендерить непроверенный HTML.
- Не хранить секреты в Git; не отправлять настоящие дипломы в общий тестовый аккаунт «Антиплагиат». В интеграционных тестах использовать искусственные документы.
- Без явной задачи не пушить, не деплоить, не отправлять внешним сервисам данные пользователя.
- После задачи отчёт: покрытые UC/FR, изменённые файлы, реально выполненные проверки, открытые риски.
